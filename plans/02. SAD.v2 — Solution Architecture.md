# 1. Purpose and What Changed

## 1.1 Purpose

This document defines the architecture of the Todo & Team Collaboration Platform when it is built **only** as vertical slices. Every feature (a story, an endpoint, a background job) is a self-contained slice that owns its request, validation, business logic, data access and response. There is no modular monolith, no module-owned databases, no inter-module contracts and no integration events between parts of the same application.

The business scope, actors, business rules and requirements from the SRD do not change. Only the way the system is organised does.

## 1.2 Summary of Changes From v1.0

| Topic | SAD v1.0 (modular monolith + slices) | SAD v2.0 (vertical slice only) |
| --- | --- | --- |
| Top-level structure | 8 business modules, each with its own slices | One application. Features are folders for navigation, **not** boundaries |
| Projects | Module projects + `.Contracts` projects + BuildingBlocks + hosts | One server project (`Todo.Server`) plus tests. Two run roles from one image |
| Database | One schema and one DbContext **per module**, no cross-schema foreign keys | One schema, one `AppDbContext`, **real foreign keys** |
| Cross-feature calls | Module contracts (`IWorkspaceAccess`, `ITodoAccess`, …) | Shared services in `Services/` used by any slice; slices never call each other |
| Side effects | Outbox, inbox, integration events, eventual consistency | Same-transaction writes through shared writers; email table acts as the queue |
| Reporting | Event-fed projection `todo_facts` | Direct SQL on the operational tables with indexes |
| Worker | Outbox dispatchers and consumers | Four small background slices (email, reminders, recurrence, cleanup) |
| Enforced boundaries | Assembly references + architecture tests | Namespace-level **slice isolation** architecture tests |
| Number of ADRs touched | 18 | 14 (Section 16) |

## 1.3 Why This Is Simpler, and What We Give Up

Gains: far fewer moving parts; strong consistency (a slice commits everything in one transaction); referential integrity enforced by the database; no event versioning, outbox, inbox or dead-letter handling; faster onboarding; easier debugging because one request is one transaction and one call stack.

Costs: module boundaries are no longer enforced by the compiler, so discipline is enforced by conventions and architecture tests (Section 6.5); the whole application scales and deploys as one unit; extracting a service later is harder than with modules (mitigation in Section 15.3).

# 2. Architectural Drivers

Carried over from the SRD and unchanged in meaning.

| Driver | Requirement | Architectural consequence in v2.0 |
| --- | --- | --- |
| Security and privacy | Personal todos visible only to the owner; workspace access by membership and role (BR-TODO-002, BR-WS-005) | Central authorization services; every query filtered by owner or membership; 404 for hidden resources |

| Auditability | Security and membership changes are recorded (FR-AUD) | `AuditWriter` called in the slice's own transaction |

| Maintainability | Different developers work on different stories in parallel | Slice isolation: a change in one slice cannot break another |
| Operability | Simple deployment for a small team (A: team size) | One container image, one database, two run roles |

# 3. Architectural Principles

| ID | Principle | Meaning in practice |
| --- | --- | --- |
| VSA-1 | **Feature first, not layer first** | Code is organised by what the user does (`CompleteTodo`), never by technical layer (no `Controllers/`, `Services/` per entity, `Repositories/`) |
| VSA-2 | **A slice owns its whole path** | Route, binding, validation, authorization call, business logic, queries, response and tests live together |
| VSA-3 | **Maximise cohesion inside a slice, minimise coupling between slices** | A slice may be changed or deleted without touching another slice |
| VSA-4 | **Slices never call slices** | No slice references another slice's types or handler. Reuse goes through `Domain/`, `Services/` or `Common/` |
| VSA-5 | **Rule of three for sharing** | Duplicate small logic once. Extract to shared code only when a third slice needs it and the behaviour is genuinely the same |
| VSA-6 | **Rich entities for invariants, slices for use cases** | Rules that must always hold (a completed todo has `completed_at`) live in `Domain/` entities. Workflow lives in the slice |
| VSA-7 | **One slice, one transaction** | A handler calls `SaveChangesAsync` once. Notifications, activity, audit and email-queue rows are written in that same save |
| VSA-8 | **Query what you need** | Read slices project straight to response DTOs with EF Core `Select` or SQL. No generic repository, no loading aggregates to read data |
| VSA-9 | **Explicit over magic** | No MediatR pipeline, no hidden conventions. A handler is a plain class with a `HandleAsync` method that is easy to follow in a debugger |
| VSA-10 | **Security is not optional per slice** | Every endpoint declares authorization. Architecture tests fail the build otherwise |

# 6. Slice Anatomy and Rules

## 6.1 One File Per Slice

A slice is a static class named after the use case, in one file. Everything the slice needs is nested inside it.

```csharp
namespace Todo.Server.Features.Todos.CompleteTodo;

public static class CompleteTodo
{
    public sealed record Request(Guid Id);
    public sealed record Response(Guid Id, string Status, DateTimeOffset CompletedAt);

    public sealed class Endpoint : IEndpoint
    {
        public void Map(IEndpointRouteBuilder app) =>
            app.MapPost("/api/v1/todos/{id:guid}/complete", async (Guid id, Handler h, CancellationToken ct) =>
                (await h.HandleAsync(new Request(id), ct)).ToHttp())
               .RequireAuthorization().WithName("CompleteTodo").WithTags("Todos");
    }

    internal sealed class Handler(AppDbContext db, ICurrentUser user, ITodoAccess access,
        IActivityWriter activity, INotificationWriter notify, TimeProvider clock)
    {
        public async Task<Result<Response>> HandleAsync(Request r, CancellationToken ct)
        {
            // load, authorize, call the entity method, write side effects, SaveChangesAsync once
        }
    }
}
```

If a slice grows beyond about 250 lines, it becomes a folder (`Request.cs`, `Handler.cs`, …) with the same names. It remains one slice.

## 6.2 What a Slice May Depend On

| May depend on | May not depend on |
| --- | --- |
| `Common/*` | Another slice (any type in another `Features/<Area>/<Slice>` namespace) |
| `Domain/*` (entities, enums, value objects) | `Features/*` from `Common`, `Domain`, `Services` or `Infrastructure` (dependencies point inward only) |
| `Services/*` (shared application services, Section 7) | Controllers, base handler classes, generic repositories |
| `Infrastructure/Persistence` (`AppDbContext`) | Another slice's request or response types |
| Its own nested types | `DateTime.UtcNow` (use `TimeProvider`) |
| The area's `_Shared` namespace, for slices in the **same** area | Cross-area `_Shared` namespaces |

## 6.3 Handler Order of Operations

1. Validate shape and range (`ValidationFilter` on the endpoint, FluentValidation validator nested in the slice).
2. Load what is needed (tracked for writes, projected `AsNoTracking` for reads).
3. Authorize through a shared service. Not visible → 404. Visible but not allowed → 403.
4. Call the entity method that enforces the invariant.
5. Write side effects through shared writers (activity, notification, audit, email queue, reminder rescheduling).
6. `SaveChangesAsync` **once**. Everything commits or nothing does.
7. Map to the response.

## 6.4 Sharing Rules (VSA-5)

| Situation | Where the code goes |
| --- | --- |
| Used by one slice | Inside that slice |
| Used by several slices of one area and tied to that area | `Features/<Area>/_Shared` |
| An invariant of an entity (always true, regardless of use case) | `Domain/` entity method |
| Used by slices of different areas and business-meaningful (access checks, notifications) | `Services/` |
| Purely technical (paging, Result type, problem details) | `Common/` |

A shared service must have at least three callers or protect a security rule (access checks always live in `Services/`, even for two callers). Shared code is reviewed more strictly than slice code.

## 6.5 Enforcement: Architecture Tests

Run on every build with NetArchTest or equivalent.

| ID | Rule |
| --- | --- |
| AT-01 | **Slice isolation:** no type in slice A references a type in slice B (a different `Features/<Area>/<Slice>` namespace). `_Shared` of the same area is allowed |
| AT-02 | `Common`, `Domain`, `Services` and `Infrastructure` do not reference `Features` |
| AT-03 | `Domain` references no EF Core, no ASP.NET Core and no `Infrastructure` |
| AT-04 | Every `IEndpoint` calls `RequireAuthorization` or an explicit `AllowAnonymous` |
| AT-05 | `DateTime.UtcNow`, `DateTime.Now`, `DateTimeOffset.UtcNow` are not used |
| AT-06 | No `Request` record has `UserId`, `OwnerUserId`, `AuthorUserId` or `CreatedByUserId` |
| AT-07 | `IgnoreQueryFilters` appears only in an allow-listed set of slices |
| AT-08 | Entities have no public setters (state changes go through methods) |
| AT-09 | DI container validates on build, with no constructor cycles |

# 7. Shared Services

Shared services replace v1's module contracts. They live in `Services/`, use `AppDbContext` directly (one database), and are the **only** place where cross-area rules are implemented.

| Service | Responsibility | Used by |
| --- | --- | --- |
| `ICurrentUser` | Authenticated user id, session id, global roles, MFA flag, time zone | all slices |
| `IWorkspaceAccess` | Membership lookup, role, permission check against the role matrix, workspace status. Cached per request only | todos, collaboration, organization, scheduling, reporting, workspaces |
| `ITodoAccess` | Single source of truth for "can this user view or edit this todo" (personal ownership, workspace role, Guest assignment) returning `AccessDecision` | every slice that touches an existing todo |
| `IActivityWriter` | Adds a `todo_activities` row to the current `DbContext` | todo and collaboration slices |
| `INotificationWriter` | Applies the recipient's preferences, composes localized text, adds `notifications` and `email_deliveries` rows to the current `DbContext` | assignment, comments, reminders, membership slices |
| `IAuditWriter` | Adds a security or workspace audit row | identity, admin, workspace slices |
| `IEmailQueue` | Adds an `email_deliveries` row (with encrypted payload for one-time links) | identity, workspace slices, `INotificationWriter` |
| `ITokenProtector` | Data Protection wrapper for one-time tokens and queued email payloads | identity, invitations |
| `IReminderScheduler` | Recomputes or cancels reminder rows when a todo is completed, deleted, moved or changes due date | todo slices |
| `RecurrenceCalculator` | Pure function: next occurrence for a rule, DST-safe (NodaTime) | scheduling slices |

Writers **add rows to the caller's `AppDbContext` and never call `SaveChangesAsync`**. The slice owns the transaction.

# 8. Data Architecture

## 8.1 Principles

- One PostgreSQL database, one schema (`app`), one `AppDbContext`, one migration history.
- **Foreign keys are used** wherever a row cannot exist without another (todo → owner user, member → workspace, assignment → todo). Orphans are impossible by construction.
- Tables and columns are snake\_case; enums are stored as text with `CHECK` constraints; ids are UUID v7 generated in code; timestamps are `timestamptz` in UTC.
- Soft delete (`deleted_at`) for todos, comments, workspaces, categories and tags, with a global EF query filter.
- Optimistic concurrency on `xmin`, exposed as an ETag.
- Migrations are applied by a separate migrator step, never by the API at startup. Destructive changes use expand, migrate, contract over two releases.

## 8.2 Table Groups (full DDL in the TDD)

| Area | Tables |
| --- | --- |
| Identity | ASP.NET Identity tables, `user_sessions`, `security_audit_events` |
| Todos | `todo_items`, `subtasks` |
| Workspaces | `workspaces`, `workspace_members`, `workspace_invitations`, `workspace_audit_events` |
| Collaboration | `todo_assignees`, `todo_comments`, `todo_comment_revisions`, `todo_watchers`, `todo_activities` |
| Organization | `categories`, `tags`, `todo_tags` |
| Scheduling | `recurrence_rules`, `scheduled_occurrences`, `reminders` |
| Notifications | `notifications`, `notification_preferences`, `email_deliveries` |

There is **no** outbox, inbox or projection table. `email_deliveries` is the only queue and is written in the same transaction as the business change.

## 8.3 Reading Data

- List and detail slices select exactly the columns they return (`Select` into a DTO). Tags, assignees and counts are fetched with joins or one batched second query, never in a loop.
- Workspace Guests are restricted by joining `todo_assignees` in the same query.
- Tag, category and assignee filters are ordinary joins (no cross-boundary lookups, which v1 needed).
- Dashboards and reports are aggregate SQL over `todo_items` (with `FILTER` clauses and `AT TIME ZONE`), supported by partial indexes. If measured latency exceeds the budget, add materialised views or a read replica later. No premature projection.

## 8.4 Consistency Without Events

| Need | v1 mechanism | v2.0 mechanism (same transaction) |
| --- | --- | --- |
| Activity history | Consumer of Todos events | `IActivityWriter` adds the row in the slice |
| In-app notification | `Notifications` consumes an event | `INotificationWriter` adds the row in the slice |
| Email | Event, then email queue, then sender | `IEmailQueue` adds `email_deliveries`; the worker sends it |
| Workspace deletion cascade | Events consumed asynchronously by 4 modules | Set-based `UPDATE` statements in the deleting slice, batched if large |
| Member removed → unassign, cancel reminders | Event consumers | The removing slice runs the same statements |
| Category deleted → clear on todos | Consumer | Foreign key `ON DELETE SET NULL` or one `UPDATE` |
| Reminder consistency after todo change | Consumer of `TodoUpdated` | `IReminderScheduler` call inside the todo slice |
| Dashboard data | Projection updated by consumer | Query on live data |

Result: no eventual consistency inside the application. The only asynchronous steps are the ones that must be asynchronous: sending email, firing reminders, generating recurring todos.

# 9. Security Architecture

Unchanged in intent from v1; simplified in implementation.

| Topic | Decision |
| --- | --- |
| Authentication | ASP.NET Core Identity with a first-party cookie (`__Host-todo.auth`, HttpOnly, Secure, SameSite=Lax). No JWT for the SPA |
| Sessions | `user_sessions` row per login; `sid` claim; cookie validation checks revocation and security stamp (cached 30 s) |
| MFA, recovery codes, external logins, passkeys | Identity features; passkeys behind a feature flag (needs .NET 10) |
| CSRF | Antiforgery token in `X-XSRF-TOKEN` for every state-changing request |
| Authorization | Two-layer: authenticated policy at the endpoint, then `IWorkspaceAccess` / `ITodoAccess` in the handler. Hidden resources return 404 |
| Global roles | `StandardUser`, `SupportAdministrator`, `PlatformAdministrator`. Global roles never grant access to workspace data |
| Rate limiting | ASP.NET Core rate limiter on auth, resend and invitation endpoints |
| Secrets | Environment or secret store. Never in logs, audit data or events |
| One-time tokens | Generated through `UserManager` or `ITokenProtector`; invitation tokens stored hashed (SHA-256) |
| Audit | `IAuditWriter` in the slice transaction; audit tables are insert-only for the application database role |

# 10. Background Processing

The worker role runs four **background slices**, each a `BackgroundService` in its feature folder, plus a daily cleanup.

| Slice | Area | Interval (proposed) | Work |
| --- | --- | --- | --- |
| `ProcessEmailQueue` | Notifications | 5 s | Claim `Queued` or `RetryScheduled` rows, render, send, retry with backoff |
| `ProcessReminders` | Scheduling | 30 s | Claim due reminders, create the in-app notification and email through `INotificationWriter`, mark `Sent` |
| `GenerateRecurringTodos` | Scheduling | 60 s | Claim due rules, create occurrences idempotently, advance the rule |
| `ExpireInvitations` | Workspaces | 15 min | Mark overdue pending invitations `Expired` |
| `RunRetentionCleanup` | Platform | daily | Purge soft-deleted todos after 30 days, expired sessions, old audit rows per policy, completed account deletions |

All claiming uses `FOR UPDATE SKIP LOCKED` with a lease column, so several workers can run at once. Idempotency comes from unique constraints (for example `(recurrence_rule_id, occurrence_number)` on todos) and from status transitions guarded in the `UPDATE ... WHERE status = ...` clause. Because side effects are written in the same transaction as the status change, a crash re-runs the step without duplicates.

# 11. API Architecture

- REST over HTTPS under `/api/v1`; JSON camelCase; ISO 8601 UTC timestamps.
- Minimal APIs. Each slice maps its own route(s) through `IEndpoint`; `Program.cs` discovers all endpoints by assembly scan.
- Errors use RFC 9457 Problem Details with a stable `code`, plus `correlationId` (same contract as v1).
- Offset pagination `page` / `pageSize` (max 100) with a deterministic sort and `id` tiebreaker.
- OpenAPI document generated from endpoint metadata. A snapshot test and a breaking-change check run in CI. The frontend types are generated from it.
- Optimistic concurrency with `ETag` and `If-Match` on updates.

The API contract (routes, status codes, error codes, resource shapes) is **identical to v1**, so the frontend and any API consumer are unaffected by this architecture change.

# 13. Observability, Deployment and Operations

| Topic | Decision |
| --- | --- |
| Logging | Structured logs (Serilog or equivalent) with `CorrelationId`, hashed `UserId`, `Feature`, `Slice`. Never emails, tokens, passwords or comment text |

# 14. Testing Strategy

The slice is the unit of testing.

| Level | What | Tooling |
| --- | --- | --- |
| Slice integration (primary) | Each slice is called through HTTP against a real PostgreSQL container: happy path, every error code, authorization rows, persisted data and side-effect rows (notification, activity, audit, email queue) | `WebApplicationFactory`, Testcontainers, Respawn |
| Entity unit | Every invariant and illegal transition in `Domain/` entities | xUnit |
| Pure logic unit | `RecurrenceCalculator` with DST golden tables, validators, permission matrix | xUnit |
| Architecture | Rules AT-01 to AT-09 (Section 6.5) | NetArchTest |
| Security | Generated IDOR sweep from OpenAPI, role-matrix tests, CSRF, session revocation, rate limits, secret-leak log test | custom suite |
| Concurrency | Parallel requests on the same todo, invitation, reminder, recurrence rule | xUnit with real database |
| End-to-end | Critical journeys from SRD section 16.4 | Playwright (including `axe-core`) |
| Performance | Read and write mixes at 10,000 todos per user, worker backlog | k6 |

Because slices are isolated, a failing slice test points to one folder, and tests run in parallel safely when each collection owns its database.

# 15. Evolution

## 15.1 Growing the Team

Ownership is by feature area (`CODEOWNERS` on `Features/<Area>`). Two developers on different slices rarely touch the same files. Shared folders (`Domain`, `Services`, `Common`) require review by the Tech Lead.

## 15.2 Keeping the Codebase Healthy

- Architecture tests fail the build on slice-to-slice references.
- A quarterly review looks at `Services/` for classes with unrelated responsibilities and at duplicated slice code that has reached three copies.
- A slice that grows beyond about 250 lines is split into a folder, not into shared helpers.

## 15.3 Extracting a Service Later

If one area needs independent scaling (for example Notifications or Reporting), extract it along the existing seams:

1. The area's slices already form a folder with no slice-to-slice references.
2. Its tables are known (Section 8.2). Replace foreign keys that cross the cut with scalar ids and add an outbox for the data the other side needs.
3. Replace calls to `Services/` that the area uses with an interface and an in-process adapter, then a remote adapter.

This costs more than extracting a v1 module, which is the accepted trade-off for the simpler system today. The trigger is measured load or team size, not preference.

# 16. Architecture Decision Records

| ID | Decision | Rationale | Consequence |
| --- | --- | --- | --- |
| ADR-001 | Vertical Slice Architecture is the only structuring principle. No modules | Smallest team-friendly structure that keeps changes local | Boundaries are enforced by tests, not assemblies |
| ADR-002 | One backend project (`Todo.Server`) and one deployable image with run roles | Less build, CI and deployment overhead | One scaling unit; roles allow separate scaling of API and worker |
| ADR-003 | One PostgreSQL schema, one `AppDbContext`, foreign keys enabled | Integrity enforced by the database; simple queries and joins | Any slice can read any table, so access rules live in shared services |
| ADR-004 | A slice is a static class in one file (nested request, response, validator, handler, endpoint) | Everything for a use case is visible together | Large slices become folders |
| ADR-005 | Slices never reference other slices; sharing through `Domain/`, `Services/`, `Common/` with the rule of three | Prevents hidden coupling | Some deliberate duplication is accepted |
| ADR-006 | No mediator library, no generic repository, no base handler | Explicit code, fewer abstractions | A few lines of repeated wiring per slice, covered by the template |
| ADR-007 | Same-transaction side effects through shared writers; no outbox, no inbox, no integration events | Strong consistency and far less infrastructure | Notification, activity and audit rows are part of the slice's save |
| ADR-008 | `email_deliveries` is the only queue; the worker claims rows with `SKIP LOCKED` | Transactional by construction | Email throughput is bounded by database polling, adequate for the SRD volumes |
| ADR-009 | Reporting reads operational tables directly; no projections | Simplest correct answer at the expected volume | Add indexes or materialised views if latency budgets are missed |
| ADR-010 | Cookie authentication with ASP.NET Core Identity, first-party, same site | Unchanged from v1 (XSS and token-theft resilience for a browser SPA) | SPA and API are deployed under one site |
| ADR-011 | Authorization in two layers: endpoint policy then `IWorkspaceAccess` / `ITodoAccess` in the handler; hidden resources return 404 | Central rules, consistent disclosure behaviour | Access services are security-critical shared code |
| ADR-012 | Soft delete with global query filter; restore window 30 days | Meets SRD recovery needs | `IgnoreQueryFilters` is allow-listed by test |
| ADR-013 | Optimistic concurrency on `xmin` with ETag and `If-Match` | No extra column, standard HTTP semantics | PATCH and PUT require `If-Match` |
| ADR-014 | API contract unchanged from v1 | Frontend and clients unaffected | Routes keep their v1 names |

ADRs from v1 that are **retired**: module-per-schema, `.Contracts` projects, per-module outbox and inbox, event versioning, Reporting projection.

# 17. Impact on Other Documents and Migration From v1

## 17.1 SRD

No requirement changes. Update only:

- Section on constraints and architecture preferences: replace "modular monolith" with "vertical slice architecture, single deployable".
- Assumption and open-question tables: remove references to module ownership and event consistency; add "Reporting reads live data" as an accepted assumption.

## 17.2 USAC (User Stories and Acceptance Criteria)

- Stories and acceptance criteria are unchanged.
- **Part XIII (module and slice mapping):** replace each "Module / Slice" pair with "Feature area / Slice"; the slice names stay the same. Remove the module-ownership notes.
- Definition of Done: replace "module boundaries respected" with "slice isolation test green".
- Cross-functional criteria that mention events or eventual consistency (for example notifications "after the event is processed") now read "in the same transaction as the change".

## 17.3 Mapping From v1 Modules to v2 Feature Areas

| v1 module | v2 feature area | Notable simplification |
| --- | --- | --- |
| Identity | `Features/Identity`, `Features/Admin` | Same slices; Admin split out for clarity |
| Todos | `Features/Todos` | Tag and category filters are plain joins; recurrence factory contract disappears |
| Workspaces | `Features/Workspaces` | Delete and member removal run set-based SQL instead of events |
| Collaboration | `Features/Collaboration` | Activity written directly by slices; no activity recorder consumer |
| Organization | `Features/Organization` | Category and tag deletion handled by foreign keys or one `UPDATE` |
| Scheduling | `Features/Scheduling` | Reminder recomputation through `IReminderScheduler` instead of event consumers |
| Notifications | `Features/Notifications` | No event consumers; writer service plus the email-queue worker |
| Reporting | `Features/Reporting` | No projection; direct SQL |

## 17.4 Migration Order (greenfield or early development)

If code from v1 already exists: collapse module projects into `Todo.Server` area by area, merge DbContexts into `AppDbContext` with one baseline migration, replace each outbox write with the matching shared writer call, delete consumers and the dispatcher, then turn on the architecture tests. If no code exists yet, start directly from the structure in Section 5.

# 18. Risks and Mitigations

| ID | Risk | Mitigation |
| --- | --- | --- |
| R-01 | Slices drift into shared-code sprawl (`Services/` becomes a dumping ground) | Rule of three, review of shared code by Tech Lead, quarterly cleanup |
| R-02 | Slice isolation erodes without compiler enforcement | AT-01 in CI, code owners, review checklist |
| R-03 | Authorization bugs because any slice can query any table | Mandatory `ITodoAccess`/`IWorkspaceAccess`, IDOR sweep, role-matrix tests, code review on every query touching user data |
| R-04 | One large transaction makes slices slow (workspace delete) | Set-based SQL, batching, performance test on large workspaces |
| R-05 | Whole application scales as one unit | Run roles, stateless API, indexes, read replica later; extraction path in Section 15.3 |
| R-06 | Live reporting queries slow at large volume | Partial indexes, query review, materialised views as the next step |
| R-07 | Email provider outage backs up the queue | Retry with backoff, alert on queue age, provider abstraction |
| R-08 | .NET 10 or passkey support differs from assumptions | Spike in sprint 1; passkeys behind a feature flag |
