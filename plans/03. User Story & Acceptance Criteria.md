# PART I — DELIVERY AND STORY STANDARDS

# 1. User Story Format

Each story follows:

**As a** [user/actor]

**I want** [functionality]

**So that** [business value].

Example:

As a registered user,

I want to create a personal todo,

So that I can organize and track my work.

# 2. Acceptance Criteria Format

Acceptance criteria use Given / When / Then.

Example:

**AC-001 — Successful creation**

Given an authenticated user,

When the user submits a valid todo title,

Then the system creates a personal todo owned by that user,

And returns HTTP 201 Created.

**AC-002 — Unauthenticated access**

Given an unauthenticated visitor,

When the visitor submits a create-todo request,

Then the system returns HTTP 401 Unauthorized.

**AC-003 — Invalid input**

Given an authenticated user,

When the user submits an empty title,

Then the system returns HTTP 400 Bad Request,

And no todo is created.

# 3. Definition of Ready (DoR)

A story is ready for development when:

- Business objective is understood.
- User role is identified.
- Acceptance criteria are defined.
- Dependencies are identified.
- Required permissions are documented.
- API behavior is understood.
- UI expectations are documented.
- Business rules are clear.
- Open questions are resolved or explicitly accepted as assumptions.

# 4. Definition of Done (DoD)

A story is complete when:

- All acceptance criteria pass.
- Backend implementation is complete.
- Frontend implementation is complete, when applicable.
- Input validation is implemented.
- Authorization is implemented.
- Unit tests pass.
- Integration tests pass.
- Relevant E2E tests pass.
- API documentation is updated.
- Error handling is implemented.
- Code review is approved.
- QA signs off.

# EPIC EP-IAM-001: Identity and Account Management

**Module:** Identity

**Business objective:** Allow users to securely register, authenticate, manage their accounts and protect their identities.

## FEATURE F-IAM-001: Registration

### US-IAM-001 — Register with Email and Password

**Priority:** P0

**As a** visitor,

**I want** to register using my email and password,

**So that** I can create an account.

Preconditions:
- Visitor is not authenticated.
- Registration is enabled.

Acceptance criteria:

**AC-001: Successful registration**

Given a visitor provides a valid unique email and password,

When the visitor submits registration,

Then the system creates a new account,

And assigns the default user status,

And sends an email confirmation message.

**AC-002: Duplicate email**

Given an account already exists with the submitted email,

When another visitor attempts registration,

Then registration is rejected,

And the system does not create another account.

**AC-003: Invalid password**

Given a password does not satisfy the configured Identity password policy,

When registration is submitted,

Then the system returns a validation error.

**AC-004: Invalid email**

Given the submitted email is invalid,

When registration is submitted,

Then the system rejects the request.

**AC-005: Unconfirmed account**

Given an account has been created but email confirmation is pending,

When the user attempts normal login,

Then access is restricted according to the configured confirmation policy.

Dependencies:
- ASP.NET Core Identity.
- Email delivery.
- Identity persistence.

Development tasks:
- Create ApplicationUser.
- Configure Identity.
- Implement RegisterUser slice.
- Implement RegisterUser validator.
- Implement email confirmation token generation.
- Integrate email provider.
- Create Vue registration page.
- Create registration integration tests.

### US-IAM-002 — Confirm Email Address

**Priority:** P0

**As a** registered user,

**I want** to confirm my email address,

**So that** my account can be activated.

Acceptance criteria:

**AC-001**

**AC-002**

Given the token is invalid or expired,

When the user submits the confirmation request,

Then confirmation fails with a suitable error.

**AC-003**

Given the email is already confirmed,

When the user opens an old confirmation link,

Then the system responds safely without duplicating or reversing the confirmation state.

**AC-004**

Given a successful confirmation,

Then the frontend displays confirmation success.

Development tasks:
- ConfirmEmail slice.
- Token validation.
- Confirmation endpoint.
- Confirmation result page.
- Unit and integration tests.

### US-IAM-003 — Resend Email Confirmation

**Priority:** P1

**As a** registered user,

**I want** to request a new confirmation email,

**So that** I can activate my account if the original email expires.

Acceptance criteria:

- Unconfirmed users can request a new email.
- A new confirmation token is generated according to Identity token-provider rules.
- Previously issued tokens are handled according to the configured token validation policy.
- Confirmed users receive a generic safe response.
- Requests are rate-limited.
- The response does not expose unnecessary account-existence information.

### US-IAM-004 — Register Through Workspace Invitation

**Priority:** P1

**As an** invited visitor,

**I want** to register using my invitation,

# PART XIV — CROSS-FUNCTIONAL ACCEPTANCE CRITERIA

These criteria apply to multiple modules and should be included in shared QA test suites.

## 1. Authorization

- A user cannot retrieve another user's private todo.
- A user cannot access a workspace without membership.
- A removed workspace member loses access.
- A guest cannot perform administrator-only operations.
- A global platform role does not automatically grant workspace access.
- Every resource mutation checks authorization on the server.

## 2. Data Integrity

- Invalid relationships are rejected.
- Duplicate memberships are prevented.
- Duplicate active invitations are handled.
- Concurrent task updates do not silently overwrite each other.
- Failed transactions do not leave partial business records.
- Outbox messages remain consistent with business transactions.

## 3. Background Processing

- Jobs can be retried safely.
- Duplicate event delivery does not duplicate business effects.
- Failed email delivery is observable.
- Recurrence generation is idempotent.
- Cancelled reminders are not processed after cancellation takes effect.

## 4. Time Handling

- Database timestamps are stored consistently in UTC.
- User time zones are stored as IANA time-zone identifiers.
- Recurring schedules use local time-zone rules.
- Daylight-saving transitions are handled.
- Date-based reporting uses explicit time-zone boundaries.

## 5. API Consistency

- Input validation is consistent.
- Authentication errors use the agreed status codes.
- Pagination follows a consistent contract.
- Errors use ProblemDetails.
- API contracts are documented.
- Sensitive data is never returned unintentionally.
